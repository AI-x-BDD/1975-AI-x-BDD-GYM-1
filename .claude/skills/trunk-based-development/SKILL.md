# Trunk-Based Development

閱讀 [方法與來源](references/methods.md)。網站的工程建議不是格式標準；下列授權與紀錄要求是本 Skill 的 Agent 實務延伸。

## 開發前

- 查閱 AGENTS.md、貢獻指南與 CI。執行 `git status --short --branch`、`git branch --show-current`、相關 diff；辨識實際 trunk、upstream、現有變更與測試命令，不假設 trunk 一定叫 main。
- 無 repository、detached HEAD 或 trunk 無法確認時，先完成可行的唯讀檢查並說明限制；不要擅自初始化或切換。工作目錄有變更時保留原狀，不自動 stash/reset。
- 檢查 manifest、測試設定與 CI 工作流程，執行有意義的基準檢查。區分既有失敗和新增回歸；缺依賴或無法執行需具體回報。

## 選擇工作方式

遵循專案規則與使用者既有要求。小團隊、低並行寫入、快速可靠測試且允許直接提交時，可在 trunk 工作；需要 PR、保護規則或並行作者較多時，使用短期分支。不要只按人數判斷，Agent 也會增加寫入頻率。

分支應是可快速審查及整合的一個工作單位，不是等整個大功能完成的隔離區。官方建議幾天內結束，超過約兩天需留意長期化；這是風險訊號，不是自動刪除或強制 merge 的條件。審查等待也計入生命週期，rebase 不會讓原始工作真的變年輕。Commit 日期不是可靠的分支建立時間，缺乏紀錄時標示未知。

## 逐步交付

1. 將需求切成可獨立測試、相容、可安全整合的小增量；不只按檔案拆分。為每一片指定可觀察驗收條件。
2. 未完成功能若能安全停用，評估 feature flag，確保預設行為安全、停用時無意外資料或外部副作用，測試有意義的開關狀態。標記擁有者與移除條件，避免永久增加分支組合。
3. 大型替換評估 Branch by Abstraction：包住舊實作 → 加入相容的新實作 → 驗證與切換 → 移除舊路徑及多餘抽象。每一步保持可用；跨資料版本變更需有相容遷移，flag 不能回復已破壞的資料。
4. 對每個增量跑相關測試；整合前執行專案要求的 build、unit、integration 等 gate，必要時確認與最新 trunk 的相容性。在未更新 remote refs 時不要聲稱已對最新遠端驗證。
5. 失敗時暫停該增量整合，診斷並修正授權範圍內問題；無法排除則記錄阻塞。不能跳過失敗檢查或僅因本地分支綠燈聲稱主幹可部署。

## 整合與授權

使用者要求開發不必然代表要求 commit 或共享操作。核對既有授權，範圍內可執行的工作持續完成。push、merge、刪分支及歷史改寫不得由本 Skill 自行授權；待整合成果可先完成並回報。不要把每日整合目標當成跳過審查的理由。

主幹若已紅燈，優先恢復可信狀態，依專案流程提出 fix-forward 或 revert；實際共享操作仍需授權。release branch 是可接受例外，但不應成為另一條長期功能開發線。

回報工作分支、各增量、分支建立時間（已知時）、commit SHA、測試命令與結果、整合狀態。明確區分「本地完成」「等待審查」「已整合」；沒有發生的動作寫未執行。判斷 TBD 應看整合頻率、分支實際存活、主幹 gate 和可交付增量，不只看分支名稱。建立時案例見 [驗證紀錄](references/validation.md)；[原始 prompt](references/original.prompt) 僅供追溯。
