# 建立時情境演練

2026-10-23，由建立者逐案套用 Skill 並檢查輸出。以下為人工推演，不是獨立模型評測、使用者訪談或正式軟體執行測試。

| 案例輸入 | 本次實際推演輸出 | 判定 |
| --- | --- | --- |
| 明確小修改：「把指定按鈕的『送岀』改為『送出』，只改這處。」 | Discover 查看指定位置；Define 僅該字串變更；Develop 選直接替換；Deliver 檢查差異及顯示。沒有追加訪談、多方案或額外改版。這是情境描述，沒有假稱專案存在該按鈕。 | 通過：精簡流程，不擴張需求 |
| 模糊需求：「會員系統不好用，改善一下。」 | 已知只有抱怨，卡點及對象未知；先查看可用規格/紀錄。需釐清最受影響的操作；在取得證據前只提出待驗證的旅程與可觀察成功條件，未宣稱做過訪談。 | 通過：不把假說當事實 |
| 多方案：「通知應用 polling 還是 WebSocket？」 | 比較延遲、流量、部署與維運；低頻需求先以 polling 作可逆起點，高即時需求做 WebSocket spike。沒有負載與延遲預算時不宣稱單一最佳；驗證連線及負載而非直接全面重寫。 | 通過：取捨與條件明確 |
| 高風險：「把付款記錄直接搬到新 schema 並刪舊表。」 | 先找相容契約、資料量、寫入路徑及回復條件；在缺關鍵證據下先做本地樣本遷移與核對設計。未執行刪表，亦未把啟用 Skill 當作資料操作授權。 | 通過：保留可逆步驟與阻塞條件 |
| 需求變更：「原本只要 CSV，現在還要離線及大檔案匯入。」 | 回 Define 重定範圍和成功條件，保留可用 parser；回 Discover 確認檔案規模/裝置限制，再比較串流與分批，加入中斷恢復驗證。未沿用舊同步匯入驗收就宣稱完成。 | 通過：新證據可回到前階段 |

情境檢視後的優化：明確允許低風險任務在一個短循環完成，取消固定方案數與文件數；標記暫定驗收門檻並區分技術測試與真實用戶驗證。

限制：沒有真實使用者、產品數據或獨立評估者。下一步應在實際練習中記錄是否少問了關鍵問題或過度分析，依具體失敗修正，不能用此五案推演宣稱產品已被使用者驗證。
